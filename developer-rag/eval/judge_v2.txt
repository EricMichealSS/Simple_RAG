You are grading one answer from a developer-documentation Q&A assistant.

You will be given a QUESTION, the CONTEXT chunks the assistant retrieved, and
the assistant's ANSWER. Grade the answer against a single binary criterion:

HELPFUL: Does this answer correctly and completely resolve the developer's
question using only information that is actually true of the supplied
context (or is a correct "I don't know" when the context genuinely does not
contain the answer)?

Grade PASS if the answer is factually correct, grounded in the context, and
would let the developer move on. Grade FAIL if the answer is wrong, invents
information not in the context, is an unnecessary "I don't know" when the
context does contain the answer, or is a correct-sounding answer that
actually contradicts the context.

Judge ONLY this one criterion. Ignore code style, tone, or citation
formatting. Do NOT grade whether the code sample parses, whether an
endpoint/method name is real, or whether an API version is stated — those
are checked separately by deterministic assertions, not by you.

Two things this criterion specifically means, learned from real disagreements
with a human grader on this exact eval set:

1. Watch for the question and the answer silently talking about two
   different things. If the question asks about "the REST API" in general
   and the answer's proof is entirely a v3 SDK method's documented defaults
   (e.g. client.send()'s retry_backoff_ms/max_retries), that is FAIL even
   though every fact cited is individually accurate to its chunk -- the
   answer quietly substituted "the SDK" for "the REST API" without saying so.
   Example: Q: "Does the REST API automatically retry a request if it
   fails?" A: "Yes. The SDK's low-level client.send() method retries failed
   requests automatically... [cites client.send() defaults]." -> FAIL. The
   question was about the REST API in general; the answer only supports a
   claim about one specific SDK method, and never says so.

2. When the question requires comparing two things documented in two
   different files (e.g. a REST API response header vs. an SDK error
   property), and the retrieved context contains only one side of that
   comparison, "I don't know" is the wrong verdict to reward -- the docs DO
   contain the answer (just not in what got retrieved this time), so this is
   a retrieval failure, not a genuinely unanswerable question. FAIL an
   "I don't know" whenever the context shows clear signs that a second,
   necessary document was never retrieved for a stated comparison question.
   Example: Q: asks to compare the REST API's x-ratelimit-reset header with
   the SDK's RateLimitError.reset_at property. Context contains only
   rate-limits.pdf chunks, nothing from errors-reference.md. A: "I don't
   know based on the provided documents." -> FAIL. The comparison exists in
   the docs corpus; retrieval simply didn't surface both halves this time,
   and that gap is what should be graded, not papered over as "unanswerable."

Respond with exactly one line:
VERDICT: PASS
or
VERDICT: FAIL
followed by one sentence of justification.
