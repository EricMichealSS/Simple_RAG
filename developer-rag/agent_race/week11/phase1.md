# Phase 1 — Observability Schema Design

**Status: COMPLETED**

## Objective

Design the per-request and per-span telemetry fields before touching `agent.py`'s code, so
Phase 2 implements a planned schema instead of scattering ad-hoc log statements.

## Why needed

`agent.py`'s existing `log` list already had SOME of what's needed (iteration number, tokens,
tool name, truncated result preview) but none of: a stable trace ID, a timestamp, per-call
cost, the prompt version active for that call, or enough of the tool's result to recover a
context/chunk ID later. Designing the full field list first avoids a second, piecemeal
instrumentation pass.

## Starting state

`agent.py`'s `log.append(...)` calls (pre-Phase-2) carried, per event:
- `llm_call`: `event, iteration, prompt_tokens, completion_tokens, cumulative_tokens, cumulative_cost_usd`
- `tool_call`: `event, iteration, tool, args, result_preview` (string, truncated to 200 chars)
- `budget_exceeded`: `event, budget, ...`

## Schema adopted (request level)

```
trace_id            -- generated per extracted/investigated request (uuid4 hex, 16 chars)
timestamp           -- UTC ISO-8601, generation time of the trace record
input_type          -- "developer_question" (this track's only request shape)
status              -- agent.py's own run_agent() status: "pass" | "budget_exceeded"
model               -- from pricing.MODEL, already centrally defined
prompt_version      -- agent.PROMPT_VERSION, NEW constant added in Phase 2
application_version -- git-commit-relative label (string, not auto-derived -- see Phase 4 note)
latency_ms          -- total wall-clock, REAL when available, labeled ESTIMATED/UNAVAILABLE otherwise
input_tokens/output_tokens/total_tokens -- summed from the log's own llm_call entries (REAL)
cost_usd            -- pricing.cost_usd() applied to the tokens above (CALCULATED)
context_ids         -- recovered from tool_call log entries' now-captured result_full
error_type          -- null unless a budget_exceeded/provider error occurred
```

## Schema adopted (span level)

```
span_id, parent_span_id, trace_id  -- parent_span_id = the owning trace_id (this track has
                                       no nested sub-agent spans within one run_agent() call,
                                       so span nesting is one level deep -- flagged honestly
                                       rather than inventing deeper nesting that doesn't exist)
span_name            -- "generation:llm_call_N" | "retrieval:search_docs" | "tool:<name>"
start_time           -- UTC ISO-8601 (NEW -- did not exist before Phase 2)
duration_ms          -- REAL where measurable, else ESTIMATED/UNAVAILABLE with a provenance note
status               -- "ok" | "error"
input_tokens/output_tokens -- per-call, not just cumulative (NEW)
cost_usd             -- per-call (NEW -- previously only cumulative cost existed)
context_ids          -- per tool span, from the tool's real result
```

## Requirements satisfied

- One trace/correlation ID per request: satisfied at extraction time (`extract_trace.py`
  generates one `trace_id` per `run_agent()` call it wraps). **Not yet generated inside
  `run_agent()` itself for every ordinary call** — see Phase 2's scope note; this is a named,
  disclosed gap, not a silent omission.
- UTC timestamps: every `llm_call`/`tool_call` log entry now carries one.
- Explicit status/error: preserved from the existing `status`/`budget_hit` fields, untouched.
- Prompt version + model identity: `PROMPT_VERSION` constant + existing `pricing.MODEL`.
- Retrieved context IDs: recoverable via the new `result_full` key (previously only a
  200-char truncated string existed, which for multi-result tool calls often cut off the
  very metadata (`source_file`, `page`) a context ID needs).
- Token usage at the model-call level (not just cumulative): new `cost_usd` per `llm_call`
  event.
- No API keys/secrets logged: confirmed — nothing in `agent.py`'s log ever included
  `GROK_API_KEY` or request headers; this was true before and remains true.
- Searchable by OUTPUT content, not just input: `deprecation_assertions.py`'s forbidden-term
  check operates on `result["answer"]`, the generated text, directly.

## What was deliberately NOT added in this pass, and why

- No OpenTelemetry spans — see `tool_selection.md` Section 2.
- No redaction/retention policy engine — this track's fixtures contain no personal data or
  secrets to redact; a real deployment handling real user questions would need one, named as
  a gap in `final_review.md`, not built speculatively here.
- No `trace_id` generated by `run_agent()` itself for every ordinary call (only by the
  `week11/extract_trace.py` wrapper) — adding a `uuid` import and a trace_id-per-call to
  `run_agent()`'s own `finish()` would be the natural next step and is named explicitly in
  `final_review.md`'s recommendations; deferred here to keep Phase 2's edit to `agent.py` as
  small and low-risk as possible (additive keys only, no new control flow).

## Acceptance criteria — verified

- [x] Schema documented above, before Phase 2 touched any code.
- [x] Every field required by the brief's own trace.json spec (per-span latency, tokens,
      cost, prompt version, context IDs) has a designed source.
- [x] Compatible with the existing stack — no new dependency implied by the schema itself.
- [x] Fields are populatable from actual `agent.py` execution, not invented post hoc (proven
      in Phase 2/4 by actually running the instrumented code).
